# Macrotask vs Microtask: приоритеты и рендеринг

## Зачем это нужно

В 06.5a ты увидел три актёра event loop: call stack, Web APIs и очереди. Теперь разберёмся, **почему** их две — macrotask и microtask — и как они влияют на то, что видит пользователь. Понимание приоритетов позволяет писать код, который не ломает UI и не создаёт race conditions.

> **Опорные концепты:** Event loop, Promise, setTimeout, call stack.

---

## Главное

### Одна итерация event loop

```
┌──────────────────────────────────────────────────────────┐
│  Итерация event loop                                     │
│                                                          │
│  1. Взять ОДНУ задачу из macrotask queue                 │
│     → выполнить до конца (стек должен опустеть)          │
│                                                          │
│  2. Выполнить ВСЕ задачи из microtask queue              │
│     → пока очередь не пуста (новые тоже выполняем!)      │
│                                                          │
│  3. Проверить, нужен ли рендер (60fps ≈ каждые 16.7мс)   │
│     → если да: обновить DOM, стили, layout, paint        │
│                                                          │
│  4. Повторить с шага 1                                   │
└──────────────────────────────────────────────────────────┘
```

### Microtask — «срочные» задачи

```js
Promise.resolve().then(() => console.log("A"));
console.log("B");
// B, A — микротаска выполняется СРАЗУ после текущего скрипта
```

**Когда используются:**
- Promise.then/catch/finally
- queueMicrotask()
- MutationObserver

**Свойство:** все микротаски выполняются подряд, без рендеринга между ними.

### Macrotask — «обычные» задачи

```js
setTimeout(() => console.log("A"), 0);
setTimeout(() => console.log("B"), 0);
// A, B — но между ними event loop может отрендерить!
```

**Когда используются:**
- setTimeout/setInterval
- addEventListener колбэки
- fetch/XHR колбэки
- I/O операции

**Свойство:** одна macrotask за итерацию. Между итерациями может быть рендер.

### Сравнение через сценарий

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => {
  console.log("3");
  Promise.resolve().then(() => console.log("4"));
});

Promise.resolve().then(() => console.log("5"));

setTimeout(() => console.log("6"), 0);

console.log("7");
```

**Трассировка:**
```
Синхронно:              1, 7
Microtask queue:        [3, 5] → выполняем 3 → добавляем 4 → выполняем 5 → выполняем 4
                        3, 5, 4
Macrotask queue:        [2, 6]
Следующая итерация:     2
Следующая итерация:     6

Итог: 1, 7, 3, 5, 4, 2, 6
```

### Рендеринг и производительность

```js
// Проблема: блокируем рендер микротасками
function bad() {
  Promise.resolve().then(function loop() {
    heavyWork();
    Promise.resolve().then(loop); // бесконечно добавляем микротаски!
  });
}
```

```js
// Решение: yield через setTimeout, чтобы дать рендерить
function good() {
  function step() {
    heavyWork();
    setTimeout(step, 0); // macrotask — event loop может отрендерить между шагами
  }
  step();
}
```

**Правило:**
- Если нужно сделать много работы без блокировки UI → используй macrotask (setTimeout)
- Если нужно гарантировать выполнение ДО рендера → используй microtask (queueMicrotask)

### queueMicrotask — явный API

```js
console.log("A");
queueMicrotask(() => console.log("B"));
console.log("C");
// A, C, B — тот же приоритет, что и Promise.then
```

`queueMicrotask` делает намерение явным: «это должно выполниться до рендера».

## Пример кода

### Разница в производительности

```js
// Вариант 1: микротаски — блокируют рендер
let microCount = 0;
function microLoop() {
  if (microCount++ < 100) {
    Promise.resolve().then(microLoop);
  }
}
microLoop();
// Страница зависнет на время всех 100 итераций

// Вариант 2: макротаски — позволяют рендерить
let macroCount = 0;
function macroLoop() {
  if (macroCount++ < 100) {
    setTimeout(macroLoop, 0);
  }
}
macroLoop();
// Между итерациями браузер может обновить UI
```

### React и microtasks

React использует микротаски для пакетного обновления состояния (batching):

```js
// В React 18+ это одно обновление, а не два:
function handleClick() {
  setCount(c => c + 1); // не рендерит сразу!
  setFlag(f => !f);     // не рендерит сразу!
  // оба изменения применятся в одном микротаске
}
```

## Частые ошибки

**Ошибка 1: Думать, что микротаски «легче» макротасков**

```js
// Этот код зависнет:
function lock() {
  Promise.resolve().then(lock);
}
lock();
```

*Почему возникает:* микротаски не волшебно быстрее. Они просто выполняются раньше. Бесконечный цикл микротасков = бесконечный цикл, без рендера.

**Ошибка 2: Пытаться «оптимизировать» через Promise.then вместо setTimeout**

```js
// НЕ делай так для отложенной работы:
function defer(fn) {
  Promise.resolve().then(fn); // микротаска — рендер не успеет!
}

// Делай так:
function defer(fn) {
  setTimeout(fn, 0); // макротаска — рендер может произойти
}
```

**Ошибка 3: Неправильный порядок при смешивании**

```js
setTimeout(() => console.log("timeout"), 0);
Promise.resolve().then(() => console.log("promise"));
queueMicrotask(() => console.log("microtask"));
// promise и microtask выведутся до timeout — всегда!
```
