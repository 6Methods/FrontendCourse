# Deep Research: Замыкания, промисы и event loop

## Контекст

Мы перерабатываем образовательный курс по JavaScript (Obsidian vault, 340+ markdown-файлов). Целевая аудитория: взрослые без CS-бэкграунда и студенты вузов. Формат: асинхронные markdown-уроки с менторской поддержкой.

Уже применена методология на основе Cognitive Load Theory + визуализация памяти + Predict the Output для модуля "Объекты" (разбито на 4 мини-урока с диаграммами стека/кучи). Результат успешен — студенты перестали воспринимать объекты как "справочник фич".

## Текущие проблемы

### 06.1 "Замыкания и this"
- Две огромные темы в одном уроке (~120 строк)
- Нет диаграмм scope chain / execution context
- Нет predict-the-output с таймингами
- `this` частично дублирует урок 05.5b (уже разобран там)
- Замыкание объясняется как "рюкзак" без визуализации

### 06.3 "Промисы и async/await"
- Справочник состояний (`pending` → `fulfilled` → `rejected`)
- Нет визуализации: что происходит в памяти при `new Promise`?
- Нет диаграмм микротасков / очередей
- Нет постепенного перехода: callback → Promise → async/await
- Задания слишком простые ("напиши wait(ms)")

### 06.5 "Event loop"
- Изолирован от промисов (отдельный урок)
- Студенты не связывают `Promise.then` с микротасками
- Нет единой картины: где живут setTimeout, fetch, then, render?

## Задания для исследования

### 1. Замыкания: визуализация и когнитивная нагрузка

- Как визуализировать **scope chain**, **outer lexical environment reference**, **environment record** в ASCII-диаграммах для markdown?
- Какие метафоры работают лучше всего:
  - "рюкзак" (замыкание уносит переменные)
  - "сфотографированный snapshot" (функция запоминает scope на момент создания)
  - "чердачная комната" (переменные живут, пока на них есть ссылка)
- Должны ли замыкания и `this` быть в одном уроке или разделены? (this уже частично покрыт в 05.5b)
- Какие **predict-the-output** задания лучше формируют понимание замыканий?
- Как объяснить, что замыкание — это не фича, а **неизбежный побочный эффект** структуры языка?

### 2. Промисы: от состояний к микротаскам

- Как визуализировать **жизненный цикл Promise** в памяти?
  - где хранятся состояние, value, onFulfilled-колбэки?
  - что происходит при `resolve()` — синхронно или асинхронно?
- Как объяснить, что `.then()` **регистрирует** колбэк, а не выполняет его сразу?
- Как связать промисы с event loop: куда именно попадает then-колбэк (microtask queue)?
- Как построить **прогрессию**: callback hell → Promise → async/await?
  - Каждый следующий шаг должен решать проблему предыдущего
- Какие задания дают "а-ха" момент про асинхронность?

### 3. Event loop: единая картина

- Как объяснить разницу **microtask vs macrotask** без перегрузки новичка?
- Как связать в одной диаграмме:
  - `setTimeout(fn, 0)` → macrotask queue
  - `Promise.then(fn)` → microtask queue
  - `requestAnimationFrame(fn)` → render queue
  - `fetch()` → network thread → callback → promise resolution
- Какие **ASCII-диаграммы** наиболее эффективны для понимания?
- Какое практическое задание наглядно демонстрирует порядок выполнения?

### 4. Структурные решения

- Разбить 06.1 на два мини-урока? ("Замыкания" + "this в глубине" или оставить this в 05.5b?)
- Нужен ли отдельный урок "Callback → Promise → async/await: эволюция"?
- Как связать 06.3 (промисы) и 06.5 (event loop), чтобы они не были изолированными?
- Нужна ли визуализация **call stack** в замыканиях и промисах?

### 5. Практика и отладка

- Как интегрировать **DevTools Sources / Async stack traces** в обучение?
- Какие задания с `console.log` + тайминги лучше показывают порядок выполнения?
- Как научить студентов **читать** асинхронный код (trace by hand)?
- Какие антипаттерны в обучении асинхронности создают хрупкое понимание?
